# Workflow: что покрыто тестами, а что нет

Документ для тестового инженера. Описывает автотесты, добавленные в `FUSIO-1202` (коммит `a475c25a`)
для фичи Workflow: что именно проверяется на уровне API (jest), что на уровне UI (Playwright),
и какие сценарии остаются на ручную проверку.

## 1. Что за фича

Workflow ограничивает переходы задачи между статусами и навешивает на переход правила.

Объектная модель (`plugins/workflow/src/schema`):

- **Workflow** - набор переходов, привязан к паре «тип проекта + тип задачи», имеет
  `initialStatuses` (список статусов, с которых задача может стартовать).
- **WorkflowTransition** - переход: `from` (список статусов, `null` или пустой массив = «любой»),
  `to` (целевой статус), плюс три вида правил.
- **Правила перехода**:
  - **Validators** - блокируют переход: `FieldRequired`, `SubtaskStatus`, `ParentStatus`.
  - **Post-functions** - выполняются после успешного перехода: `UpdateFieldValue`, `ClearFieldValue`.
    Значение может быть константой, полем самой задачи, полем родителя или пресетом
    (`$currentUser`, `$now`), и прогоняется через цепочку функций-трансформов.
  - **Requests** - экран (Screen), который показывается пользователю при переходе. Реализован
    **только на клиенте** (`plugins/workflow-resources/src/middleware.ts`).
- **ProjectWorkflow** - миксин на проекте, связывает тип задачи с конкретным workflow.
- **Screen** - набор вкладок и полей; используется правилом Request.
- **Import/export** (`plugins/workflow/src/transfer.ts`) - выгрузка/загрузка конфигурации workflow
  и экранов в переносимый JSON, где все ссылки записаны по имени.

Ограничение переходов применяется на сервере (`server-plugins/workflow/src/middleware.ts`), поэтому
обойти его через API нельзя - это и проверяют API-тесты.

## 2. Где лежат тесты и как их запускать

| Уровень | Путь | Технология | Объём |
| --- | --- | --- | --- |
| API | `ws-tests/api-tests/src/__tests__/workflow.*.test.ts` | jest против живого стенда | ~160 проверок, ~27 с |
| UI | `tests/sanity/tests/workflow/*.spec.ts` | Playwright | 35 тестов, 2 сьюта |
| Unit | `plugins/workflow/src/__tests__/`, `server-plugins/workflow/src/__tests__/` | jest, моки | 111 проверок |

### API-тесты

Требуют поднятого стенда `ws-tests` (`ws-tests/docker-compose.yaml` + `ws-tests/prepare.sh`,
который создаёт workspace `api-tests` и пользователя `user1/1234`).

```
cd ws-tests/api-tests
rushx api-test -- workflow          # только workflow-тесты
```

Переопределяется через переменные окружения: `API_TESTS_URL` (по умолчанию `http://localhost:8083`),
`API_TESTS_WS` (по умолчанию `api-tests`).

Фикстуры - `workflow.fixtures.ts`: одно соединение на jest-worker, создание типов проектов, проектов,
задач и смены статусов через `TxOperations`.

### UI-тесты

```
cd tests/sanity
rushx uitest -- tests/workflow      # или dev-uitest против локального dev-стенда
```

Оба сьюта - `test.describe.configure({ mode: 'serial' })`: одна страница и один
свежесозданный workspace на сьют, тесты идут по цепочке и зависят друг от друга. Падение
одного теста роняет следующие - это осознанный компромисс ради скорости.

## 3. Что покрыто API-тестами

Всё, что относится к серверной логике и модели данных. UI не участвует.

### `workflow.transitions.test.ts` (28) - ограничение переходов

- Переход разрешён/запрещён в зависимости от объявленных transitions; обратный переход, петля
  на предыдущий статус, терминальный статус.
- `from: null` и `from: []` трактуются как «любой статус» (тут был найден дефект в серверном
  middleware, см. раздел 6).
- Мульти-исходный переход: разрешены все перечисленные статусы, остальные блокируются.
- Полный линейный workflow, запрет перепрыгивания шага, workflow без переходов блокирует всё.
- `initialStatuses`: ограничение стартового статуса, пустой и отсутствующий список.
- Привязка: без привязанного workflow разрешено всё; ограничивается только привязанный тип задачи;
  два типа задач; один workflow на два проекта; workflow не «протекает» между проектами одного типа;
  снятие привязки снимает ограничение; привязка проекта после создания задачи.
- Удаление перехода из workflow сразу блокирует его.
- Обновления, не меняющие статус, не трогаются.
- Текст ошибки содержит статусы, из-за которых переход отклонён.

### `workflow.validators.test.ts` (35) - валидаторы

- **FieldRequired**: пустое поле блокирует, заполненное пропускает; `0` считается пустым, ненулевое
  число - нет; `null`-ссылка пустая; сообщение о первом незаполненном поле; пустой список полей
  пропускает; применяется только к своему переходу; работает на wildcard-переходе; отклонённый
  переход не меняет задачу; два валидатора на одном переходе.
- **SubtaskStatus**: родитель блокируется, пока подзадача в неразрешённом статусе; пустая карта
  статусов и `null`-запись = «любой статус»; несколько разрешённых статусов; несколько подзадач;
  типы задач вне карты игнорируются; внуки не проверяются.
- **ParentStatus**: симметричный набор для родителя; задача без родителя проходит.
- **Комбинации**: field + parent на одном переходе; subtask и parent на двух концах иерархии;
  отклонение не применяет смену статуса.

### `workflow.postfunctions.test.ts` (26 блоков + 21 параметризованный случай)

- **UpdateFieldValue**: запись константы (число, строка), перезапись значения, несколько полей
  в одном правиле, два правила на одном переходе, срабатывание только на своём переходе и на
  wildcard, копирование значения из самой задачи и из родителя (с пропуском при отсутствующем
  значении), пресеты `$now` и `$currentUser`, пустой список полей.
- **Трансформы** (параметризованно): арифметика `Add / Subtract / Multiply / Divide / Modulo /
  Power / Min / Max`, унарные `Round / Ceil / Floor / Absolute / Sqrt`, строковые
  `UpperCase / LowerCase / Trim / Prepend / Append / Replace / ReplaceAll / Cut`, цепочка из двух
  трансформов, трансформ поверх скопированного поля.
- **ClearFieldValue**: очистка числа, даты, нескольких полей; no-op на пустом поле; только свой
  переход; пустой список; совместно с update-правилом; очистка поля, установленного предыдущим
  переходом.
- **Связка с валидаторами**: post-function не выполняется, если переход отклонён, и выполняется
  после того, как валидатор удовлетворён.

### `workflow.transfer.test.ts` (38) - импорт/экспорт конфигурации

- Импорт workflow: поиск по имени, несколько workflow, переходы со статусами, `from: null`
  сохраняется, initial statuses, порядок переходов, повторный импорт переиспользует существующий
  workflow по имени.
- Ошибки импорта: неизвестный тип задачи, статус, initial-статус, экран; неподдерживаемая версия
  конфига.
- Маппинг на проекты: привязка по идентификатору проекта, два типа задач одного проекта, один
  workflow на два проекта, ошибка на неизвестный идентификатор и на ссылку на отсутствующий
  workflow, немедленное вступление в силу на живом workspace.
- Экраны: импорт с вкладками и полями, переиспользование по имени, разрешение ссылки на экран
  внутри правила перехода.
- Ссылки в правилах: статусы и типы задач внутри props валидаторов (включая ключи объектов),
  `null`-запись карты статусов, ссылки на атрибуты остаются как есть, каждому импортированному
  правилу присваивается id.
- Экспорт: пустой тип проекта, workflow по именам типов задач, переходы по именам статусов,
  маппинг проектов, обратное преобразование props в токены `$status:`/`$taskType:`/`$screen:`,
  экраны с полями.
- Round trip: экспорт равен импортированному, реимпорт в другой тип проекта, работоспособность
  workflow после реимпорта, устойчивость к JSON-сериализации.
- Clear: удаление всех workflow и экранов типа проекта, изоляция от другого типа проекта,
  возможность импортировать конфиг заново после очистки.

## 4. Что покрыто Playwright-тестами

Только UI: доступность контролов, редактирование в настройках и поведение в трекере.
Серверная логика тут проверяется поверхностно - один happy path.

### `workflow-settings.spec.ts` (24) - настройки типа проекта

- Кнопка «добавить workflow» задизейблена, пока нет ни одного типа задач, и включается после
  его создания.
- Создание workflow, тип задачи в строке списка, открытие редактора, пустой список переходов.
- Добавление переходов, в том числе перехода «из любого статуса».
- Отклонение самоперехода и конфликтующего перехода; счётчик переходов не меняется после
  отклонённых попыток.
- Открытие перехода в боковом редакторе; добавление валидатора FieldRequired и post-function
  ClearFieldValue; пометка строки перехода как «есть правила»; оба правила в списке.
- Удаление перехода, задание initial statuses, переименование workflow.
- Список классов при создании экрана: по одному на тип задачи плюс общий.
- Создание экрана, создание второго workflow для того же типа задач, удаление workflow.

### `workflow-tracker.spec.ts` (11) - применение workflow в трекере

- Модалка создания проекта предлагает настройку workflow для кастомного типа проекта, до выбора
  показывает «не настроено».
- Привязка workflow к типу задач, создание проекта с маппингом, сохранение маппинга при повторном
  открытии проекта на редактирование.
- Создание задачи в проекте с workflow; выпадающий список статусов задачи содержит только
  разрешённые workflow статусы; применение разрешённого перехода; после перехода предлагается
  следующий разрешённый статус.
- Второй проект того же типа без workflow остаётся без ограничений.

## 5. Что НЕ покрыто - зона ручного тестирования

### Не покрыто нигде

- **Requests (экран на переходе)**: показ экрана при смене статуса, обязательные поля экрана,
  отмена диалога, запись значений с экрана в задачу. Тесты покрывают только создание экрана в
  настройках и разрешение ссылки на экран при импорте/экспорте. Логика клиентская
  (`plugins/workflow-resources/src/middleware.ts`), сервер её не применяет.
- **Трансформы, не вошедшие в параметризованный набор**: `ToString`, `TextFromNumber`,
  `TextFromDate`, `TextFromCheckbox`, `NumberFromText`, `DateFromText`, `YearFromDate`,
  `MonthFromDate`, `DayFromDate`, `NumberFromDate`, `DateFromNumber`, `FirstValue`, `LastValue`,
  `Random`, `Split`, `Offset`, `DateDifference`. Их UI-редакторы
  (`transformEditors/*.svelte`) тоже не проверяются.
- **UI импорта/экспорта конфигурации**: API покрыт полностью, действия в интерфейсе - нет.
- **Диаграмма workflow** (`WorkflowDiagram.svelte`, `WorkflowDiagramPopup.svelte`) - отрисовка
  и навигация по ней.
- **`WorkflowUsedProjects` / `ScreenUsedWorkflows`** - экраны «где используется».
- **Права доступа**: поведение для пользователя без прав на настройки типа проекта.
- **Локализация**: тесты идут на английской локали; переводы правил и ошибок в остальных 10 языках
  не проверяются.
- **Приложения кроме трекера**: ограничение переходов проверено только на Issue в Tracker.
  Другие task-based приложения не проверялись.
- **Массовые операции**: смена статуса у нескольких задач сразу, drag&drop на канбан-доске,
  импорт задач - проверялось только одиночное изменение статуса.
- **Производительность**: workflow с большим числом переходов/правил, глубокие иерархии подзадач.

### Покрыто только на API, но не в UI

Здесь автотест гарантирует серверное поведение, но не гарантирует, что пользователь увидит
корректное сообщение или что контрол задизейблен:

- Тексты ошибок валидаторов в интерфейсе (какое сообщение видит пользователь при отклонённом
  переходе; API проверяет только факт отклонения и наличие статусов в тексте).
- Все валидаторы, кроме FieldRequired: `SubtaskStatus` и `ParentStatus` в UI не проверялись.
- Post-function `UpdateFieldValue` в UI не проверялась (в настройках добавляется только
  `ClearFieldValue`, и её эффект на задаче в UI не проверяется).
- `initialStatuses`: в UI проверяется только сохранение настройки, но не то, что задача не может
  быть создана в запрещённом статусе.
- Снятие привязки workflow с проекта.

### Покрыто только в UI

- Конфликты переходов (самопереход, дубль) - валидация в `AddTransitionPopup`, серверной проверки
  нет, только unit-тесты `findTransitionConflict`.
- Переименование и удаление workflow, удаление перехода.

## 6. Что стоит знать при работе с этими тестами

- **Найденный дефект**: серверный middleware проверял `t.from == null || t.from.includes(...)`,
  из-за чего переход с пустым массивом `from` блокировал всё, хотя во всех остальных местах пустой
  массив означает «любой статус». Исправлено в этом же коммите. Регресс ловит тест
  «treats an empty "from" as any status».
- **Статусы дедуплицируются на весь workspace** по `(name, ofAttribute, category)`, поэтому разные
  типы проектов делят одни и те же документы статусов. Это нормально: переходы принадлежат
  workflow, а workflow привязан к проекту через миксин `ProjectWorkflow`.
- **Особенности UI, важные при воспроизведении вручную**: дропдаун статусов перехода -
  мультиселект, он остаётся открытым после выбора и перехватывает клики; Escape закрывает вместе
  с ним и модалку. В дропдауне From у нового перехода «Any status» выбран по умолчанию - клик по
  нему снимает выбор и делает кнопку Create недоступной. Свежий тип задач Tracker приходит со
  статусами `Backlog / Todo / New state / Won / Lost`, а не со статусами дефолтного проекта.
- Подробности реализации и история отладки - в `docs/memory/workflow-tests.md`.
