# Test run telemetry

Инструменты в `tests/sanity/telemetry/`, запуск - `rushx uitest:telemetry` (обёртка `run.sh`).
Постановка задачи и статус - `platform-tasks/docs/performance/2026-08-30-001-test-run-telemetry.md`.

## Клиентские метрики (`client.ws.*`) - как устроен тракт

`ClientConnection` держит кумулятивные счётчики и отдаёт их событием `ConnectionStatsEvent`.
`packages/presentation/src/utils.ts` слушает событие, считает дельты и льёт в `uiContext.measure`,
дальше Analytics (батч 5s) -> `POST /collect` -> analytics-collector -> stats под `client/<метрика>`.

Два таймера ломали это в тестах: ping-тик, который единственный дёргал broadcast, - 10s, а батч
Analytics - 5s. Страница в sanity-тесте живёт единицы секунд, поэтому в stats не попадало ничего.
Починено с двух сторон:

- `connection.ts` вынес повторяющийся broadcast в метод `reportStats()` и кладёт
  `globalThis.__connStatsPush`. `window.__analyticsFlush` в presentation сначала зовёт его, потом
  `Analytics.flush()` - батч уходит уже со свежей дельтой, а не с тем, что застал последний тик
- `tests/sanity/tests/fixtures.ts` переопределяет фикстуру `context` и в teardown прогоняет
  `flushTelemetry` по живым страницам. Все spec-файлы импортируют `test`/`expect` оттуда, а не из
  `@playwright/test`

Переопределён именно `context`, а не auto-фикстура на `page`: auto-фикстура заставила бы Playwright
поднимать браузер и для тестов, которым нужен только `request`. Побочный эффект: страницы, созданные
через `browser.newContext()` (`getSecondPage`), под фикстуру не попадают.

## Грабли: старый бандл фронта

Front-образ стенда собирается отдельно, и `rush fast-build:docker` спокойно отдаёт бандл из кэша.
Прогон против такого бандла собирает метрики по коду, которого в нём нет - выглядит как «тракт не
работает», хотя чинить нечего. `run.sh` теперь падает до старта, если в
`sanity-front0-1:/app/dist/bundle.*.js` нет маркера `__analyticsFlush`. Обходы: `BUNDLE_CHECK=0`,
другой контейнер - `FRONT_CONTAINER`. Лечение - снести фазы `bundle` и `docker-build` в
`.fast-build-cache.json`, см. `fast_build_cache_external_deps.md`.

## Цена фикстуры: измерена, её нет

Три прогона подряд 2026-08-31 на одном sha (`39b63b3`), третий с `CLIENT_TELEMETRY=0`:

| | run1 (флеш) | run2 (флеш) | run3 (без флеша) |
|---|---|---|---|
| wall | 403.3s | 432.1s | 436.2s |
| work | 1760.2s | 1892.5s | 1969.6s |
| stats operations | 450205 | 476337 | 480935 |
| `client.ws.received` | 295 | 306 | 44 |

Прогон без телеметрии - самый медленный, но замер негодный: `restore-pg.sh` между прогонами не
звался, поэтому run3 шёл по самому грязному стенду. Сравнивался флеш на чистом стенде с
не-флешем на грязном, и видно только то, что дрейф стенда больше эффекта флеша. Корректный
замер - чередование ABBA с restore перед каждым прогоном (restore стоит 6s, так что дёшево).

Что из этих цифр всё же следует твёрдо: фикстура даёт 7x отчётов - 44 ловятся сами (длинные
тесты доживают до 10s тика), остальные 85% без неё теряются.

В проде цена нулевая: `__analyticsFlush` зовут только тесты, `reportStats()` ходит по тому же
10s ping-тику, что и до правок. Что в проде действительно стоит денег - уже существующий тракт
`client.find.duration`: analytics-collector съедает 76236 операций stats из 450205, то есть 17%
всего потока.

## Стенд копит данные между прогонами

+6.8% операций stats за два прогона подряд на одном sha, без единой правки кода. Это данные,
которые тесты оставляют в workspace, а не регресс. Отсюда два следствия:

- тезис «счётчики - свойства кода, любое изменение значимо» верен только при сбросе workspace
- `noise.js` на прогонах подряд намеряет дрейф стенда, а не шум раннера; замер шума (TSK-021)
  требует чистого workspace перед каждым прогоном

## analytics-collector: самый нагруженный сервис прогона

В прогоне 2026-08-31 коллектор дал 61 129 операций stats - больше, чем транзактор (37 120).
Причина не в нём: `uiContext.measure('client.find.duration', v)` вызывается на каждый find, а
`AnalyticsCollectorProvider` клал в очередь **отдельное событие на каждое измерение**. Пачки были
(`collectIntervalMs = 5000`), агрегации не было; при `maxBatchSize = 100` отправка шла по
заполнению буфера, а не по таймеру - около 600 запросов за прогон.

Сделано:

- клиент сворачивает окно в `{count, sum, min, max}` на пару имя+labels (`metricBuckets` в
  `packages/analytics-providers/src/analyticsCollector.ts`), событие уходит одно на метрику.
  `drainMetrics()` вызывается в начале `sendEvents()`, то есть по таймеру и по `flush()`
- коллектор принимает `count`: в stats пишется сумма, в `operations` - count, в OTLP уходит
  среднее (`server.ts`). Старый клиент без `count` работает как раньше
- из атрибутов OTLP-метрики убран `distinct_id`. Один ряд на пользователя - неограниченная
  кардинальность; в stats это уже запрещено для `error_message`, в OTLP оставалось

## Колонка Time у коллектора - не время сервиса

`recordClient` пишет `child.metrics.value += value`, а stats рисует `value` как длительность. Для
`client.find.duration` там сумма клиентских длительностей по всем браузерам: в одном прогоне 66m52s
при wall 5.7 минуты, в другом 113 287 секунд при wall 10 минут. Собственного времени у коллектора
почти нет. `collect-run.js` больше не суммирует пути `client/*` в `timeMs` сервиса.

## Что с чем сравнивать

Счётчики (число операций, байты) - свойства кода, значимо любое изменение. Тайминги на shared
runners шумят десятками процентов, поэтому порог берётся из замера: `telemetry/noise.js
runs/*/run.json` считает min/p10/median/p90/spread по нескольким прогонам одного sha. И `noise.js`,
и `compare-runs.js` отказываются работать при разном fingerprint (exit 2, снимается `--force`) -
Mac с 16 ядрами и 4-vCPU раннер несравнимы.
