# Юля ИИ (ai-bot): как работает и что проверять

Документ для QA и для тех, кто первый раз поднимает подсистему. Описывает поведение,
которое должно быть на стенде, и тест-план по областям.

Планы и статусы разработки — `foundation-tasks/aibot_rework.md`.
Топология подов и роли — `docs/aibot-deployment.md`.

## 1. Из чего состоит

```
клиент ──tx──> transactor ──> ai-queue ──> [event-router] ──> llm-<providerId> ──> [llm-router] ──> провайдер
                                    │                                                    │
                                    └──> transcription-queue ──> [stt-worker] ──> ASR    └──> billing (usage)
love (встреча) ──livekit──> love-agent ──audio──> aibot (stt-ingest) ─────────────────────┘
```

- **Реестр моделей** — yaml (`CONFIG_PATH=/var/cfg/config.yaml`). Два блока: `llm:` и `asr:`.
  В каждом `models:` (классы уровней: label, order, множители биллинга) и
  `providers[].serves:` (уровень → конкретная модель у провайдера). Один уровень обслуживает
  ровно один провайдер, иначе под падает на старте с явной ошибкой.
- **Роль пода** — `MODE`: `all` (всё в одном, дефолт для стенда), `event-router`, `llm-router`,
  `stt-worker`, `client` (clisr-воркер). Приём аудио (stt-ingest) живёт во всех ролях.
- **Уровень запроса** — свойство пространства (`AISpaceSettings.level` / `asrLevel`), каталог
  уровней отдаёт под: `GET /levels` и `GET /asr-levels`.
- **Лимиты** — считает billing, ai-bot спрашивает окна перед запросом (кэш 30 с) и слушает
  `LimitsChanged`. Локального счётчика у ai-bot нет.

Конфиги-образцы: `services/ai-bot/pod-ai-bot/config.example.yaml`, стенд — `dev/config-aibot.yaml`
(сервер) и `dev/config-aibot-client.yaml` (clisr-воркеры). Для self-host реестр генерирует
`./setup_aibot.sh` из platform-selfhost.

## 2. Подготовка стенда

1. Реестр моделей смонтирован, `CONFIG_PATH` задан. Проверка: в логе пода при старте есть
   `Transcription config` (для ASR) и не было `models.<level> not defined`.
2. Каталог планов (`plan-config.yaml`) отдан сервису payment, в нём есть блок `purchasables`
   с пакетами AI-токенов.
3. Для покупок: `PROVIDER=mock` (активация мгновенная) либо `PROVIDER=tbank` + `TBANK_MOCK=true`
   (полный конвейер со ссылкой на оплату и самоподтверждением).
4. Транскрибация: `asr:` в реестре указывает на живой endpoint; `STT_PROVIDER` не равен `none`.
5. Встречи: love-agent зарегистрирован в LiveKit. Проверка: `docker logs` агента содержит
   `registered worker`, `RestartCount` не растёт.

### Быстрая проверка, что всё живо

| Что | Как | Ожидаемо |
|---|---|---|
| каталог уровней | `GET /levels` на порт aibot | список уровней с label/order/множителями |
| ASR-уровни | `GET /asr-levels` | непусто, если настроен `asr:` |
| окна токенов | billing `GET /ai/tokens/windows` | `{month:{used,limit}, balance, available}` |
| очередь транскрибации | лог aibot | consumer joined `transcription-queue` |

## 3. Тест-план

Формат: **шаги → ожидаемо**. Где нужно — способ проверить внутри (лог, БД, API).

### 3.1 Настройки уровня

| # | Проверка | Ожидаемо |
|---|---|---|
| L1 | Настройки пространства → Юля ИИ: список уровней | видны только уровни из реестра, отключённые (`enabled: false`) отсутствуют |
| L2 | Сменить уровень, задать вопрос | ответ пришёл от модели выбранного уровня — сверить `model`/`level` в `ai_tokens_usage` |
| L3 | Уровень с `features: {tasks: false}` | инструменты задач для него недоступны, бот отвечает текстом |
| L4 | Язык пространства | ответ на языке пространства; при пустом — язык из `AI_DEFAULT_LANGUAGE` |
| L5 | Личные настройки (Настройки → Юля ИИ) | сохраняются, применяются к личным диалогам |

Уровень — свойство пространства, а не пользователя. Потолок уровня задаётся конфигом
пространства, отдельных уровней «на фичу» (talk/summary/tasks) нет.

### 3.2 Чат и контекст

| # | Проверка | Ожидаемо |
|---|---|---|
| C1 | Кнопка «Обсудить с Юлей» в шапке задачи/документа | создаётся контекст-тред; повторное нажатие переоткрывает тот же, а не плодит новые |
| C2 | «Новый контекст» в шапке треда | старый контекст архивируется, создаётся свежий |
| C3 | Вопрос в Direct с Юлей | отвечает inline в том же канале, без отдельного треда |
| C4 | Вопрос про то, что обсуждали вчера | бот вызывает `load_thread_history` и находит; без явной просьбы старую историю не тянет |
| C5 | Вопрос по документу из контекста | в ответе видно, что текст документа прочитан (TITLE/CONTENT) |

### 3.3 Инструменты: задачи

| # | Проверка | Ожидаемо |
|---|---|---|
| T1 | «Создай задачу ...» | карточка предложения: заголовок, описание, проект, подзадачи — всё редактируемое |
| T2 | Отредактировать заголовок и нажать создать | создаётся именно отредактированный вариант |
| T3 | Снять галочки с части подзадач | создаются только отмеченные |
| T4 | Запросить 20+ подзадач | модель отдаёт партиями (по 10 за вызов), карточка накапливает все |
| T5 | **Создание 5 подзадач разом** | создаются ВСЕ, не первые две — регрессия гонки, при которой liveQuery пересоздавал список по ходу цикла |
| T6 | Нажать создать дважды | повторного дубля задач нет |

### 3.4 Ассистент в диалоге создания задачи

Кнопка «Юля ИИ» в шапке диалога новой задачи (слева от крестика). Работает через тред: панель заводит
разговор с ботом в Direct (помечен `purpose: 'issue-draft'`), шлёт туда поля формы с инструкцией
и ждёт предложение. Тред остаётся в истории и не удаляется.

| # | Проверка | Ожидаемо |
|---|---|---|
| S1 | Нажать «Юля ИИ» в диалоге новой задачи | справа выезжает панель: аватар и имя бота, пресеты, штатный тред с полем ввода; диалог сдвигается, оставаясь по центру |
| S1a | Открыть диалог на телефоне | кнопки ассистента нет: диалог с разговором на узком экране не помещается |
| S1b | Записать голосовую заметку в панели | доступно - ввод штатный, как в чате; текст распознаётся и уходит Юле |
| S2 | Пресет «Подробнее» на пустой форме | приходит предложение с заголовком и описанием |
| S3 | **Печатать в форме, пока Юля думает** | ввод не блокируется и НЕ затирается ответом: предложение ждёт в панели, пока не нажали «Применить» |
| S4 | «Применить» | заголовок, описание и подзадачи попадают в форму; редактор описания показывает новый текст |
| S5 | «Вернуть» | форма возвращается к тому, что было до применения |
| S6 | «Скрыть» | предложение убирается, форма не меняется |
| S7 | Вторая инструкция подряд | уходит в тот же тред, бот отвечает с учётом первого раунда |
| S8 | Открыть Direct с Юлей после работы | тред ассистента виден в переписке, не удалён |
| S9 | Уровень с `features: {tasks: false}` | запрос всё равно обслуживается: тред помечается `feature: 'tasks'`, роутинг выбирает уровень, которому разрешены задачи |
| S10 | Создать задачу после применения | задача создаётся с применёнными полями и подзадачами |

### 3.5 Инструменты: документы

| # | Проверка | Ожидаемо |
|---|---|---|
| D1 | «Напиши документ про ...» | карточка предложения с превью markdown, кнопки Apply/Open |
| D2 | Длинный документ (просить «подробно, много разделов») | приходит целиком: модель шлёт частями (`has_more`), части склеиваются, а не затирают друг друга |
| D3 | Правка существующего документа | показывается diff, Apply меняет документ |
| D4 | Предложение, идентичное текущему тексту | сообщение «изменений нет», пустая версия не создаётся |
| D5 | Переименование | `rename_document` меняет заголовок, содержимое не трогается |

### 3.6 Лимиты вывода модели (длинные ответы)

Уровни на стенде намеренно с маленьким окном (`maxContextTokens` 8k–32k,
`maxOutputTokens` 2k–8k), чтобы предел достигался руками.

| # | Проверка | Ожидаемо |
|---|---|---|
| O1 | Попросить очень длинный ответ на слабом уровне | ответ не обрывается на полуслове: при `finish_reason=length` под дожимает продолжение (до 3 раз) и склеивает |
| O2 | То же с вызовом инструмента | tool call не теряется — в промпте модели сказано слать длинное частями |
| O3 | Очень длинная история переписки | контекст режется по окну уровня (`min(MaxContentTokens, maxContext − maxOutput)`), а не по глобальной константе |

### 3.7 Прогресс и отмена

| # | Проверка | Ожидаемо |
|---|---|---|
| P1 | Задать вопрос, смотреть на поле ввода | индикатор «↑in ↓out · N» обновляется по мере раундов |
| P2 | Нажать Cancel во время работы | запрос останавливается до следующего инструмента, приходит то, что успели собрать; статус AIRequest = `cancelled` |
| P3 | Домен `ai` в БД | документы AIRequest создаются (были невидимы, пока их клали в приватный PersonSpace) |

Ограничение: прогресс и отмена работают на провайдерах gigachat и clisr. Провайдер openai
крутит цикл инструментов внутри SDK — там ни прогресса, ни отмены.

### 3.8 Токены: два пула

Модель: **тарифное окно** (сгорает в конце периода) + **купленный баланс** (не сгорает).
Купленное тратится первым: часовой пересчёт «съедает» использование с баланса, и оно
не зачитывается в тарифное окно.

| # | Проверка | Ожидаемо |
|---|---|---|
| B1 | Панель токенов | «Доступно N», отдельной строкой «Куплено M» |
| B2 | Купить пакет (1М / 10М / 50М) | баланс вырос на номинал пакета; в `ai_token_topup` одна строка на покупку |
| B3 | Повторная доставка того же события покупки | баланс НЕ вырос второй раз (идемпотентность по `purchase_id`) |
| B4 | Потратить токены при наличии баланса | убывает баланс, тарифное окно на месте |
| B5 | Дождаться следующего периода | тарифное окно обнулилось, баланс остался |
| B6 | Исчерпать оба пула | запросы блокируются вежливым сообщением с призывом докупить токены; авто-переключения на дешёвый уровень НЕТ |
| B7 | Докупить после блокировки | работа возобновляется без перезапуска пода (кэш окон ≤ 30 с) |
| B8 | Часовой пересчёт | использование за час, попавшее в бакет ровно на границе периода, не теряется |

Учёт: почасовые бакеты `ai_tokens_usage` с разрезами `(workspace, hour, reason, provider_id,
model, level, client_id)`. Месяц — сумма бакетов за период, отдельной таблицы нет.

### 3.9 Покупка: платёжный конвейер

| # | Проверка | Ожидаемо |
|---|---|---|
| M1 | `PROVIDER=mock`, купить пакет | активируется мгновенно, баланс вырос |
| M2 | `PROVIDER=tbank` + `TBANK_MOCK=true` | выдаётся ссылка на оплату, сервис сам себе шлёт CONFIRMED-вебхук, пакет активируется |
| M3 | Разовый пакет у реального провайдера | не падает с `Unknown plan: <sku>@purchase` — цены для `purchasables` собираются наравне с тарифами |
| M4 | Смена тарифа при активном пакете | пакет не теряется, лимиты пересобираются |

### 3.10 Голос

| # | Проверка | Ожидаемо |
|---|---|---|
| V1 | Записать голосовую заметку | аттачмент создаётся, отправка сообщения НЕ ждёт распознавания |
| V2 | Дождаться распознавания | текст появляется в аттачменте `AudioTranscribe` |
| V3 | ASR-сервер выключен | через 120 с аттачмент переходит в `failed`, не висит в `pending` вечно |
| V4 | Спросить бота про нераспознанную заметку | в промпт уходит пометка «не удалось распознать», а не пустой текст |

Не реализовано: авто-стоп по тишине и покусочная транскрибация с VAD (streaming).

### 3.11 Встречи и транскрибация

| # | Проверка | Ожидаемо |
|---|---|---|
| R1 | Начать встречу с включённой транскрибацией | в логе aibot `Meeting started, connecting to Love`, состояние транскрипции обновляется |
| R2 | Говорить в встрече | реплики появляются в протоколе |
| R3 | Логи love-agent | `registered worker`, контейнер не перезапускается |
| R4 | Протокол после встречи | сохранён, привязан к встрече |

Диагностика R3: если агент циклически падает с `closing worker due to error`, включите
`LOG_LEVEL=debug`. Известная причина на старых CPU (без AVX2) — нативный биндинг
`@livekit/local-inference`, который LiveKit SDK ≥ 1.6.4 тянет ради локального EOT: он падает
с SIGILL и валит воркер. Биндинг удаляется из образа при сборке, агенту он не нужен.

### 3.12 Админка биллинга

| # | Проверка | Ожидаемо |
|---|---|---|
| A1 | Вкладка «Модели» | пулы закупки провайдера: куплено / период / израсходовано |
| A2 | Порог 80 % и 100 % пула | письмо администратору |
| A3 | Вкладка «Клиенты» | разбивка использования по `clientId` (LLM и ASR) |
| A4 | Калькулятор | из бюджета считает лимиты и прогноз |
| A5 | Разбивка по пространствам | суммы сходятся с `ai_tokens_usage` |

### 3.13 Отказоустойчивость

| # | Проверка | Ожидаемо |
|---|---|---|
| F1 | Погасить провайдера LLM | внятная ошибка в треде, под жив |
| F2 | Погасить billing | AI блокируется (fail-closed); после возврата billing работа восстанавливается |
| F3 | Перезапуск пода в середине запроса | сообщение переобрабатывается из очереди, дублей ответов нет |
| F4 | Пул провайдера исчерпан | запрос блокируется с внятной ошибкой (402), НЕ подменяется слабой моделью: раньше подмена давала мусор в ответе |

## 4. Где смотреть при разборе

| Симптом | Куда |
|---|---|
| бот молчит | лог aibot: пришло ли событие в `ai-queue`; статус AIRequest |
| «превышен лимит» | billing `GET /ai/tokens/windows`: `available`, `balance` |
| неверный биллинг | `ai_tokens_usage` по часам: разрезы `level`/`model`/`provider_id` |
| покупка не дошла | `ai_token_topup` (PK `purchase_id`), события `PurchaseActivated` |
| нет транскрипции | лог aibot `Transcription config`, доступность ASR endpoint из контейнера |
| нет транскрипции встречи | лог love-agent: `registered worker` |
| ответ оборван | включить `LLM_DEBUG=true`, искать `finish_reason` |

## 5. Известные ограничения

- прогресс/отмена не работают на провайдере openai (свой цикл инструментов в SDK);
- поиск по задачам/документам инструментом не реализован — бот не найдёт похожую задачу;
- сессия ассистента не связывается с созданной задачей (`resultId` в модели есть, не заполняется);
- отдельного UI истории AI-сессий (токены, дамп разговора) пока нет;
- BYOK (ключ клиента) не реализован;
- очередь: позиция и ETA пользователю не показываются;
- поле `tokenizer` уровня в реестре объявлено, но провайдеры его не читают — кодировка зашита;
- потоковая транскрибация с VAD и авто-стопом по тишине не сделана.
