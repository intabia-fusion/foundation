# clisr: формат кадров и глубина отправки

## Переговоры о формате

Раньше `binary` был захардкожен `true` во всех вызовах `RPCHandler` — переключателя не было
вовсе. Теперь клиент в hello предлагает список форматов, сервер выбирает первый, который умеет,
и называет его в ответе.

Формат — токен `codec/compression`: `json/snappy`, `json`, `msgpack/snappy`, `msgpack`.
Кодеки лежат в реестре `wireCodecs` (`packages/clisr/src/types.ts`); добавить cbor или protobuf —
это одна запись в реестре плюс токен в `defaultFormats`, протокол не меняется.

Кадры:

| кадр | значение |
|---|---|
| `FRAME_MSGPACK = 4` / `FRAME_MSGPACK_SNAPPY = 5` | msgpack, как раньше |
| `FRAME_DATA = 10` | `[10][compressed 0|1][тело в кодеке соединения]` |

msgpack сохраняет свои коды кадров, чтобы старый пир читал ровно то, что читал всегда; все
остальные кодеки едут на `FRAME_DATA`. Поэтому новый кодек не жрёт коды кадров комбинаторно.

Совместимость в обе стороны:

- клиент без переговоров не шлёт `formats` -> `negotiateFormat(undefined)` даёт `msgpack/snappy`;
- сервер без переговоров отвечает без `format` -> клиент остаётся на msgpack;
- сервер назвал формат, которого у клиента нет -> клиент тоже откатывается на msgpack.

Откат без пересборки: `CLISR_FORMATS=msgpack/snappy` (через запятую, лучший первым).
Дефолт — `['json/snappy', 'json', 'msgpack/snappy', 'msgpack']`. Замер, из-за которого сменили
дефолт: сжатый msgpack экономит 3% трафика, но стоит серверу вдвое дороже на упаковке
(`platform-tasks/docs/performance/2026-08-29-001-protocol-json-switch.md`).

### Клиент без msgpack (Go, Swift)

Hello — единственное место, где формат ещё не согласован. Кодировка hello **сниффится** по
первому байту: `{` (0x7b) не может начинать msgpack-тело (там это число 123), значит JSON.
Сервер парсит hello в той кодировке, в которой он пришёл, а `FRAME_HELLO_RESP` кодирует уже
согласованным кодеком. Go-клиент шлёт JSON-hello с `formats: ["json/snappy"]` и msgpack не
трогает вообще.

TS-клиент по-прежнему шлёт hello в msgpack — так его понимает и старый сервер.

Остальное для не-msgpack клиента уже готово: `FRAME_BINARY`/`FRAME_BINARY_RESP` собираются
вручную (заголовок — JSON), `FRAME_OP_STATUS`/`_RESP` — JSON, ping/pong — один байт.
Что придётся реализовать на стороне Go: конверт `TotalArray` из `rpcJSONReplacer`
(`{dataType:'TotalArray', total, lookupMap, value}`) и snappy, если не выбран `json` без сжатия.

### Грабли: JSON превращает `undefined` в `null`

`rpcJSONReplacer` возвращает `value ?? null`, поэтому явный `undefined` в массиве едет по
проводу как `null`. Ответ на server-initiated запрос — `params: [result, undefined]`, и
проверка `error !== undefined` на приёме стала истинной: сервер уходил в ветку ошибки,
`error.message` кидал TypeError, промис не резолвился, запрос висел вечно. Читатели
провода должны сравнивать через `!= null`.

Второй такой же капкан: `readResponse(data, false)` зовёт `data.toString()`, а
`Uint8Array.toString()` даёт `"123,34,..."`. JSON-тело надо декодировать в строку до разбора —
это делает кодек `json` в реестре.

## Глубина отправки на клиента

`binaryRequest`/`requestWithFilter` выбирали клиента слепым round-robin (`cindex++ % len`) и
могли навалить пачку запросов на занятого, пока соседний простаивает. Теперь
`ClisrServer.pickSession` берёт наименее загруженного (`session.requests.size`), round-robin
только разрешает ничью, и пропускает клиента, у которого уже `session.options.capacity`
запросов в полёте. Если все полны — ждёт с тем же бэкоффом, что и при отсутствии клиентов.

Резервирование слота гонки не имеет: `MeasureContext.with` зовёт свой callback синхронно, а
регистрация в `session.requests` идёт до первого `await` внутри `sendBinaryRequest`.

`capacity` не объявлен -> лимита нет, поведение как было. ASR-воркер объявляет его в
`client.request('transcription', [true, config.SttCapacity])` (`STT_CAPACITY`, дефолт 4).

### Ожидание слота — по событию, не поллингом

Первая версия при полном клиенте спала `sleepInterruptible(waitDelay)` с тем же бэкоффом, что и
при отсутствии клиентов: 100 мс -> 5 с. На батче из 8 задач семь из них уходили в этот сон, и
батч становился **медленнее** одиночного потребителя (688 мс против 528 на 200 задачах).
Теперь `waitForSlot` будит диспетчер по `notifySlotFree()` из мест, где запрос уходит из
`session.requests`; бэкофф остался только верхней границей. Штраф упал до ~9%.

### Что это даёт

`transcribe-prefetch.spec.ts` (без Kafka) проверяет на живых сокетах, что воркеру реально
приезжает `capacity` **разных** файлов одновременно, и что при `capacity=1` его батчер физически
не может собрать группу больше одного чанка.

`kafka-clisr-e2e.spec.ts` гоняет весь путь stt-worker на живой redpanda:
Kafka -> batch consumer -> `ServerProvider` -> clisr -> воркер (1-2 мс на задачу) -> обратно.
Запускается только по `AI_BOT_QUEUE_E2E=1` (`QUEUE_CONFIG`, дефолт `localhost:19093`), каждый
прогон берёт свой топик и свою группу, топики стенда не трогает.

200 задач, работа 1 мс, локальная redpanda:

| STT_BATCH | capacity | ms | мс/задача |
|---|---|---|---|
| 1 | 1 | 537 | 2.69 |
| 1 | 4 | 508 | 2.54 |
| 8 | 1 | 578 | 2.89 |
| 8 | 4 | **285** | **1.43** |
| 32 | 1 | 583 | 2.92 |
| 32 | 4 | 292 | 1.46 |

Выводы:

- **Размер пакета сам по себе не даёт ничего** и даже чуть вредит: при `capacity=1` батч едет
  через тот же одиночный слот, плюс накладные на ожидание. `STT_BATCH` без `STT_CAPACITY`
  бессмысленен.
- Пара батч+глубина даёт **1.9x** (537 -> 285).
- Потолок задаёт `capacity`, а не батч: 32 не лучше 8. Растить надо `STT_CAPACITY`.

Это транспортный замер с фиктивной работой; выигрыш самого батчинга инференса меряется на
стороне ASR-сервиса — там 2.5-8x
(`platform-tasks/docs/ai/2026-08-29-501-asr-chunking-batching.md`).
