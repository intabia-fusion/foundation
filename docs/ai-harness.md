# AI harness ai-bot: алгоритм, инструменты, промпты

Что происходит между «пользователь написал в чат» и «бот ответил». Устройство подсистемы в
целом - `docs/llm.md`, топология подов - `docs/aibot-deployment.md`, тест-план - `docs/aibot.md`.

Весь код ниже - `services/ai-bot/pod-ai-bot/`.

## 1. Границы

Наш harness не CLI-агент: нет файловой системы, нет shell, нет автономных многошаговых планов.
Есть один ответ на одно сообщение, до 8 раундов вызовов инструментов внутри, и инструменты
работают не с файлами, а с документами воркспейса (задачи, документы, треды).

Ключевое архитектурное отличие от CLI-агентов: **инструменты не применяют изменения**. Почти все
они складывают предложение (`PendingProposal`) в контекст запроса, оно приезжает пользователю
карточкой в том же сообщении, и применяет её человек. Исключение одно - `rename_document`.

## 2. Путь одного сообщения

```
tx -> trigger -> ai-queue -> [event-router] -> llm-<providerId> -> [llm-router] -> провайдер
                                                     |
                                      WorkspaceClient.processMessageEvent
```

`processMessageEvent` (`src/workspace/workspaceClient.ts:627`):

1. Разрешить `personUuid` по социальному id, отбросить собственные сообщения бота и флуд
   (`isRepliesFlooding`).
2. Собрать текст запроса: markup -> текст, дождаться расшифровок голосовых вложений
   (`collectVoiceTranscripts`), приклеить их к тексту, остальные вложения - строкой
   `Name/FileId/Type`. Не расшифрованное голосовое даёт явную пометку в промпте, чтобы модель
   сказала об ошибке, а не молчала.
3. `contextMode` = `direct`, если объект - `chunter:class:DirectMessage`, иначе `thread`.
4. Включить индикатор «печатает» (TTL 3 с, обновляется каждые 2 с, `setTypingStatus:370`) и вызвать
   `generateAndReply`.

### generateAndReply (`workspaceClient.ts:903`)

1. `askedAt = Date.now()` - фиксируется ДО чтения, чтобы сообщение, пришедшее во время
   генерации, попало в следующий ход, а не в щель между ходами.
2. Память: `getMemory` - `personalContext` из `Preference` (миграция из старого blob), плюс
   `sharedPrompt` воркспейса. Кэш 60 с, `sharedPrompt` читается всегда (у пода нет tx-фида).
3. Системный контекст объекта:
   - `Document type: <class>` (system);
   - тело корневого сообщения - **ролью `user`**, не system: авторский текст в system-роли
     позволил бы prompt injection поверх инструкций по инструментам;
   - для `AIContextMessage` («Обсудить с ассистентом») подгружается связанный объект и
     `workingContext` (черновик в диалоге создания задачи);
   - `buildDocPrompt:725` формирует блок про задачу/документ: заголовок, тело в
     ```` ```markdown ````, для задачи - список существующих подзадач и жёсткие правила, что можно
     и чего нельзя писать в `propose_new_document`.
4. История:
   - верхний уровень канала (`objectIdIsSpace`) - только сегодняшние сообщения, остальное через
     инструмент `load_thread_history`;
   - тред - читается файл-снапшот беседы, из БД добираются только сообщения новее его курсора
     (`loadSnapshot`, `snapshotMessageIds`);
   - `AIEditProposalMessage` в историю попадает не телом, а фактом («предложил правку, применена /
     не применена») - иначе черновик документа съедал бы окно;
   - `buildThreadContext` (`src/workspace/threadContext.ts`) режет по бюджету, выкидывая старое.
   - блок документа кладётся **последним**, перед самим запросом: маленькие модели «теряют
     середину».
5. Бюджет контекста: `contextBudgetFor:142` = `(maxContextTokens - maxOutputTokens) * 0.85`,
   но не больше `MaxContentTokens` (дефолт 12800). Коэффициент 0.85 - потому что подсчёт токенов
   оценочный (tiktoken на GigaChat - догадка), а забитое под завязку окно даёт 422 и потерю запроса.
6. Лимиты: `getWorkspaceWindows` + `decideLevel` (`src/workspace/windowLimit.ts`). `block` ->
   индикатор «печатает» заменяется причиной и пишется системный ответ (`notifyLimit`), запрос
   не уходит. Даунгрейд уровня переключает и провайдера, иначе биллинг ушёл бы не туда.
7. `createAIRequest` - документ-статус запроса (уровень, модель, kind, `status: processing`).
8. `getTools` + `resolveChatLanguage` -> `llm.createChatCompletionWithTools(...)`.
9. Ответ: markdown -> markup, `writeReply` пишет одно сообщение - текст плюс карточка
   из `reqCtx.pending`, если инструмент что-то подготовил.
10. `donePatch` дописывает в `AIRequest` токены и `billedTokens` с множителем модели.
11. `appendSnapshotTurn` - фоном, без await: сбой хранилища не должен ронять уже отданный ответ.

## 3. Цикл инструментов

`runToolCalls` (`src/llms/toolLoop.ts:106`) - общий для всех провайдеров, вместо `runTools` из SDK
(только он умеет прогресс и отмену).

```
ask(priorToolResults) -> reply
  reply.toolCalls пусто -> финальный ответ (+ до 3 продолжений, если обрезан)
  reply.toolCalls есть   -> исполнить на поде, добавить в priorToolResults, следующий раунд
  исчерпаны итерации / отмена -> финальный раунд БЕЗ инструментов
```

Константы и правила:

| Механика | Значение | Зачем |
|---|---|---|
| `MAX_TOOL_ITERATIONS` | 8 | потолок раундов модель<->инструменты |
| `MAX_CONTINUATIONS` | 3 | ответ упёрся в `max_tokens` -> дозапрашиваем хвост и склеиваем |
| oversize-retry | 1 раз | ответ обрезан и пуст (потерян длинный tool call) -> `OVERSIZE_HINT`: «шли по частям, `has_more=true`» |
| финальный раунд | всегда | инструменты убираются (`noTools`), модель обязана дать текст |
| отмена | между раундами | `isCancelled` читает статус `AIRequest`; инструменты пропускаются, ответ собирается из уже полученного |
| `MAX_PHANTOM_CALLS` | 3 | вызовы несуществующих инструментов за прогон; исчерпаны - выход в финальный раунд |
| прогресс | каждый раунд | `onProgress` пишет `iteration`/токены в `AIRequest`, пользователь видит счётчик |

Аккумулируются **все** результаты инструментов за прогон: выкинуть прошлые раунды - значит
спрятать от модели уже добытые данные.

**Выдуманные инструменты.** Слабые модели зовут то, чего нет (`create_task`, `get_context`,
`notify_user`). Ответ инструмента называет то, что существует: `Error: tool 'X' does not exist.
Available tools: ...` - голая ошибка модели ничего не объясняет, и она зовёт снова. Сверх того
считаются сами вызовы: три несуществующих за прогон - и цикл идёт в финальный раунд.
Считать раунды целиком фантомными было бесполезно: модель ставит один реальный вызов рядом с
выдуманным, полностью фантомных раундов не бывает, а запрос за раунд платится.

**Потолки на результаты** (`src/utils/budget.ts`). Один результат - 15% бюджета уровня, все
результаты прогона - 40%. Режется по границе строки, и в тексте сказано, сколько обрезано:
молчаливое усечение модель принимает за полный ответ. Исчерпан прогонный бюджет - следующий
результат заменяется на «отвечай по тому, что уже получено». Применяется в обёртке `getTools`
(`tools.ts:790`), а не в каждом инструменте - новый инструмент покрыт сам собой.

Продолжение обрезанного ответа (`prompts.ts:36`) отправляется как
`assistant: <текст пока что>` + `user: продолжи ровно с места обрыва`.

**Inline tool calls.** Локальные OpenAI-совместимые серверы (gpt-oss, harmony у GigaChat) без
парсера tool-calls печатают вызов текстом. `parseInlineToolCalls` (`src/llms/inlineToolCalls.ts`)
вытаскивает `<|function_call|>{...}` балансировкой скобок. Такие результаты (`id` = `inline_*`)
и обратно подаются текстом - структурный `tool_calls`-ход такая модель прочитать не может
(`openai.ts:324`). В финальном раунде они схлопываются в один digest-блок.

## 4. Каталог инструментов

`src/utils/tools.ts`. Регистрация: `registerTool(def, handler, scope, feature?, purpose?)`.
Фильтрация в `getTools`, `tools.ts:790`: по `contextMode`, по `AIFeature` уровня (слабой модели не дают то,
что она завалит) и по `purpose` (`PURPOSE_TOOLS`).

| Инструмент | Scope | Feature / Purpose | Что делает |
|---|---|---|---|
| `load_thread_history` | any | - | сообщения СТАРШЕ `beforeIso` (дефолт - начало сегодня), лимит 1..200, oldest first |
| `propose_task` | any | tasks | карточка новой задачи: title, description, priority, estimation, due_date, labels, subtasks. Ничего не создаёт |
| `edit_issue_draft` | any | tasks / `issue-draft` | правит черновик в диалоге создания задачи; единственный доступный инструмент в этом purpose (плюс history) |
| `propose_subtasks` | thread | tasks | разбиение связанной задачи; дубли по нормализованному заголовку отбрасываются |
| `list_subtasks` | thread | tasks | существующие подзадачи + застейдженные на карточке, чтобы модель не предлагала их заново |
| `propose_new_document` | thread | - | полное новое тело связанного документа/описания задачи в markdown; пользователь применяет диффом |
| `rename_document` | thread | - | **применяется сразу** - заголовок короткий и отменяемый |
| `getDataBeforeImport` | any | - | список teamspace и родителей; только если задан `DataLabApiKey` |
| `saveFile` | any | - | PDF -> markdown через datalab.to -> новый документ; только с `DataLabApiKey` |

Батчинг длинных полезных нагрузок - сквозная идея: `has_more=true` докладывает в
`reqCtx.pending`, `has_more=false` завершает. Лимит подзадач `MAX_SUBTASKS = 100`, за раз
рекомендуется <= 10. Причина: один вызов с 50 подзадачами упирается в `finish_reason=length`,
и весь function_call теряется целиком.

Ответы инструментов написаны как инструкции модели, а не как статусы: «часть принята, зови ещё
раз только с продолжением», «всё уже существует, отвечай текстом, не предлагай заново»,
«не повторяй содержимое в ответе». Это дешевле, чем пытаться описать то же в системном промпте.

`postEditProposal:877` сравнивает предложенное с текущим телом (`normalizeForCompare` - схлопывание
пробелов) и возвращает false, если изменений нет: маленькие модели любят «переписать» документ
в то же самое.

## 5. Промпты

**Язык служебного текста - английский.** Системные промпты, ответы инструментов, вставки в контекст,
сообщения об обрезке - всё на английском. Единственное исключение - `replyLanguageReminder`: там
язык принципиален и это подтверждено замером (см. раздел 8). Смешивать нельзя: русская служебная
строка среди английских инструкций сбивает модель на ответ не на том языке.


Файлы: `prompts.yaml` (системные промпты), `welcome.yaml` (приветствие). Оба переопределяются
переменными окружения `PROMPTS_PATH` / рядом с процессом в докере. Отсутствующий файл или
недостающий ключ - падение на старте, встроенных фолбэков нет (`promptStore.ts:53`).

Шаблонизатор `renderPrompt` (`src/llms/promptStore.ts:36`): `{{var}}` и условные блоки
`{{#var}}...{{/var}}`, которые исчезают при пустом значении. Подстановка значения - через
функцию-заменитель, чтобы `$&` внутри пользовательского текста не сработал как ссылка на группу.

Ключи `prompts.yaml`:

| Ключ | Где | Переменные |
|---|---|---|
| `directChatWithTools` | direct-чат | `botName`, `lang`, `currentDateTime`, `sharedPrompt`, `personalContext`, `outputLimit` |
| `threadChatWithTools` | треды и каналы | то же, без `personalContext` |
| `summarizeMessages` | саммари встречи/переписки | `lang`, `description` |
| `translateHtml` | перевод | `lang` |
| `correctTranscript` | правка расшифровки голосовой | `lang` |

Что стоит за отдельными кусками:

- `{{botName}}` - `FIRST_NAME` пода (`botName()` в `prompts.ts:43`), имя нигде не захардкожено.
- `currentDateTime` - короткий локализованный формат: полный слабые модели повторяют дословно.
- `outputLimit` - `describeOutputLimit`, `prompts.ts:124`: `maxOutputTokens` уровня, пересчитанный в символы
  (4 симв/токен, 80% запаса), с явным «за пределом текст ОТРЕЗАЕТСЯ и теряется». Пустая строка,
  если у модели потолок не задан - блок целиком исчезает.
- Раздел про инструменты в `directChatWithTools` наполовину состоит из запретов вызывать
  `load_thread_history`: сегодняшний контекст уже в промпте, но модели упорно лезут за ним.
- Память в промпте всегда, тулов для её чтения/записи нет: `sharedPrompt` и `personalContext`
  редактирует пользователь в настройках.
- Групповой промпт явно запрещает персонализацию - `personalContext` туда не попадает вообще.
- Системный промпт треда дополняется `systemMessages` из истории (`buildSystemPrompt`, `prompts.ts:102`).

`welcome.yaml` рендерится тем же `renderPrompt` при первом Direct с ботом
(`sendWelcome:1367`), локали `en`/`ru`.

### Документ, который не влезает

Тело больше 45% бюджета уровня **не режется**. Усечённое тело опаснее отсутствующего: модель
предложит новую версию по половине текста, и вторая половина исчезнет молча - заметят это уже
после применения. Вместо тела в контекст идёт:

- заголовок и оглавление (список markdown-заголовков по порядку, `documentOutline`);
- первые ~2000 символов с явной пометкой, что это только начало;
- прямая инструкция: переписать документ нельзя, поблочное редактирование в разработке, а на
  вопросы о структуре и о показанной части отвечать нормально.

Одновременно `propose_new_document` и `edit_issue_draft` **не отдаются модели** вовсе
(`ReqCtx.documentReadOnly` -> фильтр в `getTools`): инструмент, которым нельзя пользоваться, всё
равно будет вызван.

Замер на Qwen-27B, документ ~60k символов: в промпт ушло 5598 токенов вместо переполнения, модель
ответила текстом за один раунд, документ не тронут.

## 5a. Компактизация

Когда ходы перестают влезать в окно, старая часть **сжимается в summary**, а не выбрасывается.
Раньше `buildThreadContext` молча ронял самое старое: договорённость из начала разговора исчезала,
и это не было видно ни в файле, ни в промпте, ни в логе.

`src/workspace/compaction.ts` - чистая часть (что сжимать), `WorkspaceClient.compactIfNeeded` -
чтение файла, вызов модели и запись.

| Механика | Значение | Зачем |
|---|---|---|
| `CompactionReserveTokens` | 16384 | запас под ответ; сжимаем, когда ходы не влезают в `бюджет - reserve` |
| `CompactionKeepRecentTokens` | 20000 | хвост, который остаётся дословно за summary |
| точка среза | ближайший ход `user` | резать между вопросом и ответом - оставить ответ без вопроса |
| повторная компактизация | от прошлого `firstKept` | иначе ходы, пережившие прошлый раз, провалятся между двумя summary |
| compact-and-retry | 1 раз | провайдер отказал по длине - сжать принудительно и повторить |

Оба порога - дефолты pi, оба в `limits:` конфига.

Хранение: summary - это ход с ролью `summary` в том же файле-снапшоте, плюс `firstKept` во
frontmatter. Свёрнутые ходы **остаются в файле** (это и транскрипт, который скачивает человек), но
`contextTurns` перестаёт отдавать их модели.

Промпт - ключ `compactConversation` в `prompts.yaml`: фиксированная структура (что нужно
пользователю / договорённости / сделано / в работе / решения / что дальше / объекты). Отдельно
подчёркнуто держать инструкции о том, КАК работать - тон, длина, язык: их потеря самый частый
ущерб от компактизации. Прошлое summary подаётся на вход следующей.

Токены компактизации биллятся как обычный запрос, `reason: 'compaction'` - в разборе счёта видно,
сколько стоит само сжатие.

Провайдер без `compactConversation` (clisr) просто никогда не компактит: поведение остаётся прежним.

## 6. Снапшот беседы

`src/workspace/conversationSnapshot.ts` - один MDX-файл на тред в блоб-хранилище,
`ai-snapshot-<conversation>.mdx`. Frontmatter (`conversation`, `object`, `cursor`, `turns`), дальше
чанки через `---` с заголовком `## <role> · <author> · <iso>[ · <messageId>]`.

- `cursor` - `modifiedOn` самого свежего **входящего** сообщения, а не ответа: между вопросом и
  ответом могли написать другие, привязка к ответу их бы потеряла.
- Повторная доставка из Kafka не дублирует ход: ходы узнаются по `messageId`.
- `role: tool` пишется для человека, но **не подаётся модели** обратно (`workspaceClient.ts:1016`):
  прошлых раундов инструментов модель раньше не видела, и подача их назад меняет поведение.
- Потолок `SNAPSHOT_MAX_TURNS = 500` - только чтобы старый тред не рос без границ.
- Файл отдаётся кнопкой скачивания (`readSnapshotFile:1201`), плюс отдельный клиентский экспорт
  `plugins/ai-bot-resources/src/exportChat.ts`.

## 7. Что ещё вокруг цикла

- **Провайдеры** (`src/llms/`): `openai.ts` (прямой), `gigachat.ts`, `server.ts` (раздача запросов
  clisr-воркерам, инструменты сериализуются определениями, исполняются на поде), `mock.ts`.
  Все три используют один `runToolCalls`.
- **Ретраи**: `withRetry(maxRetries: 3, retryNetworkErrors)` вокруг вызова провайдера
  (`openai.ts:361`). Только сетевые ошибки; исчерпание - исключение, пользователь получает
  `AIServiceUnavailable`.
- **`</think>`**: у reasoning-моделей отрезается всё до закрывающего тега (`openai.ts:267`).
- **Биллинг**: `billUsage` на каждом раунде внутри `chatToolStep`, множитель - из реестра моделей.
- **`LLMDebug`** логирует полный messages-массив и tool-calls обеих сторон.

## 7a. Сценарные прогоны на живой модели

`services/ai-bot/pod-ai-bot/src/__tests__/eval/` - прогон сценариев через настоящий харнесс:
реальные определения инструментов (`getTools`), реальный системный промпт из `prompts.yaml`,

потому что сценарий судится по состоянию мира после последней реплики, а не по тексту ответа.

### Одна точка входа

```bash
cd services/ai-bot/pod-ai-bot
rushx eval           # судья -> модель под тестом -> допуски -> сценарии
rushx eval models    # только список того, что отдают источники
rushx eval check     # только снять профиль допуска (--all - по всем моделям)
```

Порядок вопросов: **сначала судья, потом модель под тестом**. Судья - измерительный инструмент, и
от того, что он умеет, зависит, чем вообще меряется прогон. На вопрос о модели под тестом Enter
означает «та же, что судья».

Модель в коде не зашита. Источников два: локальный OpenAI-совместимый сервер (`AI_BOT_E2E_URL`,
по умолчанию `http://127.0.0.1:8000/v1`) и GigaChat (`GIGACHAT_CREDENTIALS`, `GIGACHAT_SCOPE`,
`GIGACHAT_BASE_URL`). Недоступный источник не мешает доступному. В неинтерактивном запуске
(CI, скрипт) вопросы не задаются: `--model` / `--judge` или `AI_BOT_E2E_MODEL` /
`AI_BOT_EVAL_JUDGE_MODEL`, с префиксом источника, когда он не локальный - `gigachat:GigaChat-2-Max`.
Без `--judge` в неинтерактиве судья не назначается: судейство - необязательная половина оценки.

### Допуск модели

`eval check` гоняет проверки **через тот же `chatToolStep`, которым пользуется под** - с нашим
системным промптом и нашими определениями инструментов, а не мимо них. Результат ложится в
`eval/profiles/<source>_<model>.json`:

| Проверка | Обязательна | Зачем |
|---|---|---|
| `toolCall` | да | нативный вызов инструмента, аргументы валидным JSON |
| `toolLoop` | да | после результата инструмента даёт финальный текст, а не зовёт снова |
| `restraint` | да | не зовёт инструмент, когда он не нужен - на этом стоит весь `directChatWithTools` |
| `language` | да | отвечает на языке из инструкции (`Always reply in {{lang}}`) |
| `structuredOutput` | нет | строгая json-схема; без неё модель нельзя поставить судьёй |
| `outputCap` | нет | `finish_reason=length`; нужно продолжению обрезанного ответа |

Необязательные проверки гейтят одну возможность, а не прогон. Там, где источник не даёт нужного
транспорта (у GigaChat нет `response_format`), проверка отмечается `skipped`, а не `fail`: это
ограничение канала, а не модели.

Прогон **не стартует** без профиля, с непройденным профилем, со сменившимся эндпоинтом или когда
окно модели разошлось с записанным (модель передеплоили). Окно уровня берётся из профиля, а не из
стендового конфига, который может с ним не совпадать.

### Судья

Реализован в `eval/judge.ts`. Получает **только** требования сценария и трассу прогона -
состояние воркспейса до, реплики, вызовы инструментов с аргументами, что применилось, состояние
после. Не видит ни системного промпта, ни того, какая модель работала: с этим знанием модель
начинает оправдывать поведение вместо оценки. Ответ форсируется строгой json-схемой
(`{id, met, evidence}` по каждому требованию) - прозу от судьи разбирать незачем.

Вердикт судьи не влияет на `ok`/`FAIL` сценария: регрессию ловят ассерты, судья добирает то,
что не формализовать. В отчёте отдельная колонка `2/3 (нет: R2)`.

Что судья видит в трассе: разговор ДО прогона, реплики, вызовы инструментов с аргументами,
**подготовленные, но не применённые предложения**, состояние воркспейса до и после, и текст
summary, если во время прогона была компактизация. Каждая из этих секций появилась после того, как
судья ошибался без неё - см. ниже.

**Перед доверием судью проверяют**: `rushx eval judge` гоняет его по эталонным трассам
(`eval/fixtures.ts`) - два прогона, где работа сделана, и два, где нет. Судья, который их не
различает, к прогону не допускается.

Три случая, когда судья был формально прав, а трасса неполна - все нашлись на живых прогонах:

| Чего не видел судья | Что отвечал | Что добавлено в трассу |
|---|---|---|
| состояния ДО | «раздел не сохранён» на корректной правке | `WORKSPACE BEFORE` |
| подготовленного, но не применённого предложения | «задача не создана» на черновике формы | `prepared but not applied` |
| разговора до прогона и текста summary | «договорённость не сохранена» при удачном сжатии | `CONVERSATION BEFORE THIS RUN`, `COMPACTED INTO THIS SUMMARY` |

Отсюда правило для требований в сценариях: формулировать **наблюдаемо в трассе**. «Правит черновик
формы» судья проверить не может - UI он не видит; «вызван `edit_issue_draft`, новых задач в
воркспейсе нет» может.

Спрашивается первым. Список тот же, годные судьёй помечены (`годна судьёй` = проверка
`structuredOutput` пройдена); `0` - без судьи. Модель без строгого JSON судьёй не ставится: об этом
говорится сразу после её допуска, и прогон продолжается на одних детерминированных проверках.

Судья оценивает семантику по трассе - то, что нельзя проверить сравнением. Детерминированные
проверки от него не зависят и работают всегда.

Та же модель судьёй - дешевле всего, но она мягче к собственным результатам: вердикт судьи это
метка для разбора, регрессию ловят ассерты.

```bash
rushx eval --model 'Qwen3...' --judge 'gigachat:GigaChat-2-Max' --runs 3 --report report.md --yes
```

Сценарий - YAML в `eval/scenarios/`: мир, список реплик, ожидания по конечному состоянию
(`document.contains/notContains/title/unchanged`, `issues.count/subtasksOfRoot/titlesMatch`,
`toolsCalled`, `forbidTools`, `maxRoundsTotal`). Отчёт - таблица со сценарием, раундами, токенами,
временем, вызванными инструментами и тем, что не сошлось.

## 8. Сравнение с pi (`@earendil-works/pi-coding-agent` 0.84)

pi - CLI-агент (read/bash/edit/write/grep/find/ls, сессии-деревья, TUI). Сравнимы только
механики harness, не набор инструментов.

### В чём мы устроены похоже

- Цикл «спросить -> исполнить -> дослать результаты» с исполнением на своей стороне.
- Явные лимиты вывода в описаниях инструментов и инструкция дробить длинное на части.
- Результат инструмента как текстовая инструкция модели, а не как код возврата.
- Прогресс и прерывание вынесены в хуки поверх цикла.

### Что у pi есть, а у нас нет

| Механика pi | Наш эквивалент | Разрыв |
|---|---|---|
| Компакция: суммаризация старого хвоста по структурному шаблону, `firstKeptEntryId`, повторяемая | `buildThreadContext` просто выбрасывает старые сообщения | старое теряется бесследно |
| Recovery: переполнение контекста -> компакция -> один retry | запас 0.85 и надежда | переполнение = потерянный запрос |
| Truncation-контракт: у каждого тула лимит строк/байт, в ответе сказано, что обрезано и где полное | лимиты штучные (`limit<=200`, `listSubIssues:100`), в токенах не считаются | большой результат тула может выбить окно |
| Progressive disclosure (skills): в промпте только описания, тело грузится тулом | всё в системном промпте всегда | промпт растёт, доля запретов в нём высокая |
| Steering: сообщение пользователя доставляется после текущего хода, не после всей работы | сообщение попадает в следующий запрос | «нет, не так» не останавливает текущую генерацию |
| Хуки `beforeToolCall`/`afterToolCall` с правом заблокировать и подменить результат | `ToolLoopHooks` = только `onProgress`/`isCancelled` | нет точки для аудита и политик доступа |
| Экспоненциальный backoff, счётчик попыток сбрасывается на успешном ответе | фиксированные 3 сетевых ретрая | всплеск 429/5xx рвёт запрос |
| Очередь мутаций на файл: параллельные вызовы к одному объекту сериализуются | `Promise.all` по вызовам раунда, `reqCtx.pending` - одно поле | два `propose_*` в одном раунде затирают друг друга |

### Что брать, в порядке цены/выгоды

1. **Сериализовать вызовы, меняющие `reqCtx.pending`.** Сейчас `toolLoop.ts:191` исполняет раунд
   через `Promise.all`, а `pending` - одно поле; два предложения в одном раунде дают гонку.
   Дёшево: исполнять последовательно либо взять на `pending` очередь по образцу
   `file-mutation-queue`.
2. **Токенный потолок на результат инструмента.** Один общий хелпер обрезания с явным хвостом
   «обрезано N из M, зови с `beforeIso`/`limit`». Закрывает `load_thread_history`,
   `listSubIssues`, `getFoldersForDocuments`.
3. **Компакция вместо выбрасывания истории.** Файл-снапшот уже есть - в него же писать
   структурное summary (Goal / Constraints / Progress / Decisions / Next steps / Critical context)
   и курсор «с какого хода дальше идёт сырьё». Прямо ложится на `appendTurns`.
4. **Compact-and-retry на переполнение контекста.** Ловить 422/context-overflow, сжимать,
   повторять ровно один раз, вместо `AIServiceUnavailable`.
5. **Backoff по образцу pi**: `baseDelayMs * 2^(attempt-1)`, сброс счётчика на успехе, отдельно
   для 429.
6. **Расширить `ToolLoopHooks` до `beforeToolCall`/`afterToolCall`.** Точка для аудита, для
   политик по ролям и для «этот уровень такой инструмент не исполняет» без правки реестра.
7. **Steering.** Сообщение, пришедшее во время генерации, доставлять между раундами
   (`askedAt`-курсор для этого уже есть) - для чата это заметнее, чем для CLI.

Не берём: дерево сессий с ветвлением и суммаризацией веток, расширения-плагины,
инструменты файловой системы. Это цена CLI-агента, у нас другой профиль.

### Мелочи, которые стоит проверить

- `buildThreadContext` берёт `messages.slice(-20)` до всякого бюджета: даже при окне 128k в
  контекст не попадёт больше 20 ходов. Похоже на реликт, а не на решение.
- `skipCache = true` ставит заголовок `cf-skip-cache` на **каждый** чат-запрос
  (`workspaceClient.ts:1124` -> `openai.ts:299`). Для провайдеров с prompt-кэшем это отказ от
  скидки на длинный системный промпт. pi отключает кэш точечно - только для одноразовых
  промптов компакции.
